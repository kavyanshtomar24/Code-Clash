01 · EXECUTIVE ARCHITECTURE SUMMARY
1. Executive Architecture Summary
This document is a CTO-level technical review of the CodeClash Competitive Programming & DSA Platform. It covers every major architectural decision required to build a production-grade, portfolio-worthy system that survives resume screening at top-tier tech companies.
⚡
Architecture Decision: Modular Monolith chosen over Microservices for MVP. Reason: Lower operational complexity for a solo/small team, easier debugging, shared database transactions. The codebase is structured to extract services later without rewrites.

CREATE INDEX idx_subs_verdict    ON submissions(verdict) WHERE verdict = 'AC';
CREATE INDEX idx_subs_submitted  ON submissions(submitted_at DESC);

05 · WEBSOCKET & REAL-TIME ARCHITECTURE
5. WebSocket & Real-Time Architecture
5.1 Connection Management Design
FastAPI's native WebSocket support with Redis PubSub as the message bus. This decouples WebSocket connections from the API process — critical when you add a second server instance.
# Connection Manager (backend/app/websocket/manager.py)
class ConnectionManager:
def __init__(self):
# battle_id → set of WebSocket connections
self.rooms: dict[str, set[WebSocket]] = defaultdict(set)
self.redis = aioredis.from_url(settings.REDIS_URL)
async def connect(self, ws: WebSocket, battle_id: str, user_id: str):
await ws.accept()
self.rooms[battle_id].add(ws)
# Subscribe to Redis channel for this battle
asyncio.create_task(self._redis_listener(battle_id))
async def broadcast(self, battle_id: str, event: dict):
# Publish to Redis; listener fans out to all WS clients
await self.redis.publish(f"battle:{battle_id}", json.dumps(event))
async def _redis_listener(self, battle_id: str):
pubsub = self.redis.pubsub()
await pubsub.subscribe(f"battle:{battle_id}")
async for message in pubsub.listen():
if message["type"] == "message":
for ws in self.rooms[battle_id].copy():
try: await ws.send_text(message["data"])
except: self.rooms[battle_id].discard(ws)

07 · SECURITY ARCHITECTURE
7. Security Architecture
7.1 JWT Refresh Token Rotation
Short-lived access tokens (15 min) + long-lived refresh tokens (7 days) stored in HttpOnly cookies. On every refresh, the old refresh token is immediately blacklisted in Redis.
Security Layer
Implementation Detail
Password Hashing
bcrypt with cost factor 12. Never store plaintext. Use passlib[bcrypt]. Argon2id preferred for new systems.
JWT Strategy
Access: 15min exp, HS256. Refresh: 7d exp, stored HttpOnly cookie. Token JTI blacklist in Redis on logout/refresh.
Input Validation
Pydantic models on every endpoint. NEVER raw SQL strings — SQLAlchemy ORM only. Whitelist language values.
Code Sandbox
docker run --network=none --memory=256m --cpus=0.5 --read-only --tmpfs /tmp:size=16m --ulimit nproc=50. Container killed after time_limit + 1s.
Rate Limiting
Login: 5 attempts/5min per IP. Submission: 10/min per user. API: 100 req/min per user. Implemented via Redis INCR + EXPIRE.
CORS Policy
Whitelist only: https://codeclash.vercel.app in production. No wildcard origins.
WS Auth
JWT passed as ?token= query param on WS handshake. Validated before connection accepted. Expired tokens → close(4001).
SQL Injection
ORM-only queries. Raw SQL in Alembic migrations only. Parameterized queries enforced via SQLAlchemy Core for complex aggregations.
08 · AUTOMATED JUDGE SYSTEM
8. Automated Judge System Design
8.1 Architecture Overview
🎯
Phase 1 (MVP): Single judge worker, submissions stored immediately. Phase 2: Multiple worker processes, Docker container pool pre-warmed for lower cold-start latency.
# backend/app/services/judge_worker.py
async def process_submission(task: dict) -> Verdict:
submission = task["submission"]
problem = await get_problem(submission["problem_id"])
# 1. Write code to temp file
with tempfile.NamedTemporaryFile(suffix=ext, delete=False) as f:
f.write(submission["code"].encode())
code_path = f.name
# 2. Run Docker container
result = await run_in_docker(
image=LANGUAGE_IMAGES[submission["language"]],
code_path=code_path,
test_cases=problem.test_cases,
time_limit_ms=problem.time_limit_ms,
memory_limit_mb=problem.memory_limit_mb
)
# 3. Update DB + notify via Redis PubSub
await update_submission_verdict(submission["id"], result)
await redis.publish(f"submission:{submission['id']}",
json.dumps(result))

8.3 Verdict Decision Tree
Container exits → exit_code, stdout, stderr, elapsed_ms, peak_memory_kb
if compile failed (exit_code == 1 at compile step):
verdict = CE  (Compilation Error)
elif elapsed_ms > time_limit_ms:
verdict = TLE
elif peak_memory_kb > memory_limit_mb * 1024:
verdict = MLE
elif exit_code != 0:
verdict = RE  (Runtime Error — SIGSEGV, exceptions)
elif stdout.strip() == expected_output.strip():
verdict = AC
else:
verdict = WA

13 · RESUME-WORTHY TALKING POINTS
13. Interview & Resume Talking Points
These are precise, technically accurate answers to the questions interviewers at top companies will ask about this project:
Interview Question
Strong Answer Using This Architecture
"Tell me about your architecture decision"
Chose modular monolith over microservices deliberately — lower operational overhead for MVP, codebase structured for service extraction. Judge worker is the natural first extraction candidate.
"How did you handle security for code execution?"
Docker containers with --network=none, --memory=256m, --cpus=0.5, read-only filesystem. Container killed after time_limit+1s. User code literally cannot reach the network or host filesystem.
"How does your real-time system work?"
WebSocket connections subscribe to Redis PubSub channels keyed by battle_id. Judge worker publishes verdicts to the channel. This decouples the WS server from the judge — critical for horizontal scaling.
"What was your biggest scaling challenge?"
The judge system under burst contest traffic. Solved with Redis as async queue (LPUSH/BRPOP), judge workers scaled horizontally via docker compose replicas, and per-user rate limiting to prevent queue flooding.
"How did you design the database?"
UUID primary keys for distribution safety, composite index on (user_id, problem_id) for O(1) "has user solved problem" checks, partial index on verdict=AC to make analytics cheap, JSONB for flexible test case storage.
"What trade-offs did you make?"
Leaderboard uses eventual consistency — Redis sorted set updated async, 30s stale reads acceptable vs guaranteed consistency requiring expensive DB locks. Chose availability over consistency here, classic CAP trade-off.
"How did you handle authentication?"
JWT with refresh token rotation. Access tokens expire in 15 minutes. Refresh tokens stored HttpOnly, rotated on every use. Revoked JTIs blacklisted in Redis with matching TTL.
"What would you change if you had more time?"
Extract judge into a separate microservice with proper message broker (RabbitMQ/SQS), add PostgreSQL read replica for analytics, implement connection pooling with PgBouncer, add distributed tracing with OpenTelemetry.
